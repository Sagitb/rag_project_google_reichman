01 · The problem

The answer exists. It's in ticket 417 of 1,000.

A manager asks "did we ever expose supplier pricing, and how was it fixed?" The information is in Jira, in prose, across a year of tickets. Nobody reads them all. A language model can — but a model that answers fluently without proof is worse than no model.

What the system must do

  • Answer from retrieved tickets only, and cite them inline as tckt-XXXX
  • Say "not resolved" when a ticket is a workaround, not a fix — a Done status isn't proof
  • Refuse when the evidence doesn't cover the question
  • Answer Hebrew questions over an English corpus
  • See new Jira issues without a full re-index; never write back to Jira

What we built

  • Retrieval: multilingual E5 → FAISS → BGE cross-encoder rerank
  • Generation: Gemma 4 E4B, deterministic, with a versioned grounding prompt
  • Adaptation: QLoRA adapter trained on grounded answers, selected on validation
  • Orchestration: deterministic router, evidence gates, advisory writer
  • Operations: incremental Jira sync + Gradio chat for managers
02 · Dataset

1,000 tickets that pass a contract before anything runs

Five anonymized real tickets were the seeds. LLM data augmentation expanded them to a balanced 1,000-ticket corpus (10 families × 100, seven fixed sections each), and every generated ticket went through two reviews: a manual read for realism, and a second LLM acting as judge over the full list for consistency, duplication and label correctness. Synthetic by design — the only way to ship a public repo with real ticket depth.

06 · Vector DB & retrieval

One index, five ways to ask

Semantic search is the interesting path, but a manager who types "ticket 186" or "how many High tickets are open" should get an exact answer, not a similar one. All five paths share one document schema and one validation routine.

Semantic

E5 query vector against 1,000 normalized passages; FAISS IndexFlatIP, cosine by construction.

"supplier information exposed?" → tckt-0186 @ 0.819

Lookup

ID normalization: 186, ticket 186, טיקט 186 all resolve to tckt-0186. No embedding involved.

Filter

Exact metadata predicates on status, priority, work type, component, open/closed. Case-folded, validated field names.

Aggregate

Deterministic Python counts with group-by. "Open High tickets": 92 — 85 In Progress, 7 To Do. Never generated.

Hybrid

Filter first, then rank the eligible subset by exact dot product. Result validation asserts every hit satisfies the filter.

What's in a document

{
  "document_id": "tckt-0186",
  "search":   { "embedding_text": "Summary: ...\nComponent: ...\nDescription: ..." },
  "content":  { "summary", "component", "description" },   # shown to the model
  "metadata": { "status", "priority", "work_type", "component" }, # filterable
  "evaluation": { "family", "solution_type" },  # never embedded, never prompted
  "system":   { "split": "train", "document_version": "rag_documents_v1" }
}

Integrity checks that run on every load

  • Corpus count, IDs and split counts match the vector-store contract
  • Embeddings are float32, 768-d, L2 norm 1.0 ± 1e-5
  • Vector position i maps to document i; FAISS vectors equal the NumPy matrix
  • Files on disk match the manifest hashes
  • Query vector shape, finiteness and normalization asserted per query
07 · Grounded generation

Gemma 4 answers only from what it was shown

google/gemma-4-E4B-it, bf16, greedy decoding. The prompt is a versioned file with a SHA-256 in every artifact identity, so an answer can never be silently produced by a different instruction set.

Prompt v3 — the grounding contract, in five rules

  • Answer strictly from supplied tickets; retrieval rank is a hint, not proof — don't merge merely similar incidents
  • Answer every supported part: what happened, resolved?, cause, fix, validation, prevention; state what cannot be determined
  • Call an outcome permanent / partial / workaround / unresolved only when the text supports that wording. Done alone is not a fix
  • Cite each material claim locally as tckt-XXXX, only with IDs present in the context
  • Answer in the language of the question; never expose scores, labels or reasoning

Context assembly

Top-k tickets rendered as ID, summary, component, type, status, priority, description — ranks and scores stay out. A 12,000-token budget; if a source doesn't fit, its description is trimmed by binary search on token count rather than dropped. Included, truncated and omitted IDs are recorded with the answer.

Citation validation, after every answer

validate_citations(answer, retrieved_ids)
→ { has_valid_citation: True,
    all_citations_valid: True,
    invalid_citations: [] }   # anything here = the answer is unsafe
08 · Evaluation protocol

Select on validation. Freeze. Open the test set once.

44 human-written questions with Gold ticket IDs and expected answer points. The loader proves every Gold ID belongs to the split it's evaluated on; the frozen-system file is re-read and fingerprint-checked before the test cells will execute.

8 questions are in Hebrew. No-answer questions describe plausible incidents that don't exist in the corpus — the correct answer is a refusal.

Metrics, kept separate on purpose

  • Retrieval: Hit@1, Hit@5, Recall@5, Complete@5, MRR@5 against Gold IDs
  • Citations: presence, all-from-context, Gold recall, Gold precision
  • Content: expected-point coverage (E5 similarity ≥ 0.75 per point), ROUGE-L
  • Safety: no-answer abstention, invented-citation rate, language match

The gate chain a result has to pass

GOLD_IDS_IN_CORRECT_SPLIT SELECT_ON_VALIDATION FREEZE_SYSTEM_FINGERPRINT REREAD_AND_VERIFY TEST_ONCE REPORT_FAILURES_VERBATIM

Section 13 states it explicitly: test results were used for reporting, not for selecting a rank, a prompt or a retriever. Nothing was re-tuned after seeing them.

10 · QLoRA fine-tuning

Two ranks, same schedule. Lower loss did not win.

Supervision is distant: for each train/validation ticket the target is a fixed opening by solution state + the ticket's own RESOLUTION and VALIDATION sections + its citation. Inputs are the question, 5 context tickets (the source plus 4 nearest same-split distractors) and Prompt v3. Test tickets are never seen.

how to read it

Read the arrows, not the cells

1 → 3 isolates retrieval: Gold citation recall goes from 0 to 0.97 and invented citations vanish. 3 → 4 isolates fine-tuning: coverage, precision and ROUGE-L rise, and abstention on unanswerable questions collapses. Cell 2 is the diagnostic: 65% invented citations means the adapter learned the shape of a grounded answer, not the Jira facts.

Decision

QLoRA + RAG is the primary answer path, wrapped by an evidence gate (next slides). It's the most complete and the most precisely cited system. Base + RAG stays the safer generator for unsupported questions and kept more sources on multi-ticket questions (0.75 vs 0.50). Neither No-RAG cell is a deployment option.

12 · Limitations

What we would not want you to find out by asking

abstention 0 / 2

The adapter answers everything

Two no-answer test questions; the fine-tuned model answered both. Each is 50% of the metric, so the score is 0 or 1 with nothing in between. Root cause: 22 refusal examples in 794 — too few to teach a policy. The Agent's semantic gate at 0.70 restores the refusal (harness: new-no-answer-001 → insufficient), but that's a guardrail, not a fix.

synthetic corpus

Clean data makes retrieval look easy

Every ticket has a distinct summary and a seven-section description; real Jira has duplicates, one-liners and screenshots instead of text. Hit@5 = 1.0 on 18 questions is a statement about this corpus, not about Jira. Multi-source recall (0.5–0.75) and Hebrew are the more honest signals.

template supervision

QLoRA targets were derived, not written

Targets come from each ticket's own RESOLUTION and VALIDATION sections, with three question templates per solution state. That explains the ROUGE-L gain. The test questions are human-written and phrased differently, so the behavioral gain transfers — but the adapter has never seen a human answer.

Keyword router

The Agent routes on phrases ("how many", "recommend", Hebrew equivalents). It's transparent and testable, and it breaks on misspellings and indirect phrasing. Not an LLM planner, and we don't call it one.

Hebrew generation

Retrieval is cross-lingual; generation is less natural in Hebrew than English and the abstention phrase list had to be maintained in both languages by hand.

No unit tests

Validation is runtime assertion, of which there is a lot. The pure functions — ID normalization, citation validation, ADF flattening, routing, loss masking — deserve pytest and don't have it yet.

13 · Agent guardrails

A small, deterministic layer that decides when not to generate

Every turn produces a plan before any tool runs: route, ticket ID, filters, whether generation is needed, advisory level. The plan is part of the response, so a wrong answer can be traced to a wrong decision.

Seven-scenario harness (one in Hebrew, none from the benchmark): route, evidence, citation and advisory assertions all pass. That's a test of the rules, not a language-quality score.

Evidence gates, in order

  • Top semantic score < 0.70 → insufficient, no generation
  • Generator itself abstains → state downgraded to insufficient
  • Answer says "resolved" about a cited unresolved or workaround ticket → draft withheld, human review
  • Any citation outside the retrieved set → citation_safe = false
read-only

The Advisory Writer can recommend "confirm the preventive sharing rule is still active". It cannot transition, edit or create a ticket: write_executed is hard-coded false, and "Move tckt-0186 to Done" returns a refusal. Jira is read at query time; the only write in the project is the one-time demo bootstrap of a single traceable issue.

13 · Live Jira synchronization

A ticket created in Jira is answerable after one click

Cloud REST v3, one project, issues labelled jirag-demo. Each issue is normalized into the same document schema as the corpus, hashed, and only new or changed issues are re-encoded. Live documents get IDs from tckt-1001 upward so they can be cited like anything else.

Fetch

Enhanced JQL search, paginated by token, capped at 50 for the POC. Descriptions arrive as Atlassian Document Format and are flattened to text.

Diff

SHA-256 of each normalized document against the last manifest: new / updated / unchanged / removed. Model or contract change → full re-encode.

Encode & persist

Only the delta goes through E5. Documents, embeddings, mapping, FAISS index and manifest are staged in a temp dir and swapped atomically.

Serve

Gradio merges the frozen 1,000-ticket index with the live overlay; exact lookup accepts research IDs, live IDs and Jira keys (SCRUM-2).

Conclusions

What we'd tell the next team

What worked

  • Contracts + fingerprints turned a 16-section notebook into something that reruns in minutes and can't be quietly changed after freezing
  • Multilingual E5 gave Hebrew retrieval for free; BGE reranking fixed source order (test MRR 0.97 → 1.00)
  • QLoRA on distant supervision improved completeness (all points: 0.94 → 1.00), citation precision (0.97 → 1.00) and ROUGE-L, with zero invented citations under RAG
  • The 2×2 separated the two contributions cleanly enough to make a decision from
  • Incremental Jira sync is idempotent and demo-able

What's hard

  • Fine-tuning for style silently erodes refusal behavior; 22 refusal examples don't hold the line
  • Multi-source questions: the adapter cited one of two Gold tickets half the time
  • Fluent Hebrew answers, and a router that survives typos
  • A synthetic corpus proves the pipeline, not the product
